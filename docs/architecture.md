## Два запроса к модели

Оба возвращают строгий JSON — формат задаётся схемой на стороне API, поэтому
разбирать «почти JSON» не приходится.

| | Вердикт | Уточняющий вопрос |
|---|---|---|
| Модель | `claude-opus-5` | `claude-opus-5` |
| Усердие (`effort`) | `high` | `low` |
| Лимит ответа | 8000 токенов | 2000 токенов |
| Частота | один раз за интервью | 3–6 раз |

Системный промпт побайтово одинаков во всех запросах и кешируется — после
первого обращения он почти бесплатен. Отсюда важное следствие: **не собирайте
`IDENTITY` из переменных** (дата, имя пользователя, счётчик). Любое изменение
внутри строки ломает кеш и делает каждый запрос дороже.

Обрабатываемые сбои: отказ по безопасности, обрыв по лимиту токенов,
невалидный JSON, сетевая ошибка. Любой из них — понятное сообщение
пользователю, ответы сохранены, повторить можно любым сообщением.

## Хранение

SQLite, четыре сущности. Только стандартная библиотека, без ORM: схема
маленькая, а чистый SQL делает переход на Postgres механической правкой, а не
миграцией фреймворка.

| Таблица | Что лежит |
|---|---|
| `users` | telegram_id, язык, даты |
| `sessions` | состояние, оценки, выбранная сфера, вердикт (JSON), обязательство (JSON) |
| `turns` | вся расшифровка: роль, текст, текст или голос, сфера |

Состояние пишется на каждом шаге, поэтому перезапуск посреди интервью не
теряет ответы.

Одна деталь, о которую легко споткнуться: `create_session()` сам создаёт запись
пользователя, если её нет. Раньше вызов без предварительного `upsert_user()`
падал по внешнему ключу — теперь порядок вызовов не важен.

## Стоимость

Одно завершённое интервью по ценам Claude Opus 5 ($5 / $25 за миллион токенов),
при кешируемом системном промпте примерно на 2,5 тыс. токенов:

| | Запросов | Выход | Примерно |
|---|---|---|---|
| Уточняющие вопросы | 4–7 | ~200 токенов | ~$0,03 |
| Вердикт | 1 | ~1500 токенов | ~$0,06 |
| **Итого** | | | **~$0,10** |

Локальное распознавание речи добавляет вычисления, но не стоимость API. То есть
бесплатный лимит в несколько интервью на человека вполне реален, а подписку
имеет смысл считать от ценности, а не от себестоимости.

## Тесты

67 тестов, ни один не обращается к API и не требует ключа.

| Файл | Что проверяет |
|---|---|
| `test_library.py` | Целостность библиотеки, включая выдуманный идентификатор |
| `test_flow.py` | Состояния сессии, запись и чтение из базы, `/forget` |
| `test_render.py` | Полнота переводов, определение языка, кризисный скрин, экранирование |
| `test_bot.py` | Полный проход интервью на подставных объектах Telegram |
| `test_docs.py` | Что собираемые справочники не разошлись с кодом |

Тесты `test_bot.py` подменяют Telegram простыми заглушками — обработчики
используют небольшую часть его API, так что это быстрее и надёжнее живого бота,
и ловит именно ошибки маршрутизации и переходов.

Два реальных дефекта были найдены при написании этих тестов: падение
`create_session()` по внешнему ключу и отсутствие ограничения на число
уточняющих вопросов в самом цикле бота (оно было только в движке).

## Чего не хватает

**Нет проверки качества вердиктов.** Тесты подтверждают, что механика работает,
но не то, что совет хороший. Нужен набор из 20–30 реалистичных расшифровок с
оценкой: та ли сфера названа и достаточно ли мелкое действие предложено. Без
этого любая правка промпта — угадывание. Это самая ценная следующая работа, и
для неё нужны живые расшифровки.

**Нет цикла возврата.** Обязательства сохраняются, текст обещает вернуться с
вопросом, но задание, которое напоминает, не написано. `past_commitments()` в
`db.py` и планировщик из python-telegram-bot уже на месте. Стоит сделать: у
отслеживания прогресса приличная доказательная база (`change.harkin2016`), то
есть это не только про удержание.

**Один процесс.** SQLite и опрос Telegram предполагают единственный экземпляр.
Для нескольких понадобятся Postgres и вебхуки.

**Нет ранжирования библиотеки.** В запрос уходят все записи по нужным сферам.
На 28 работах это нормально; на нескольких сотнях понадобится отбор по
смысловой близости.
